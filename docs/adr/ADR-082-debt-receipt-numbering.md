# ADR-082: Debt-Receipt Numbering Reuses customer_ledger Sequence

Status: ACCEPTED
Date: 2026-10-06
Session: SESSION-ARC-007, Reply 6

## Context

TASK-BRK-060 required a decision on how a printed debt-payment receipt (a
non-sale print job) would be numbered. CTP-SESSION-ARC-007 Section 12 item 6
asked whether to introduce a new `document_sequences` key (e.g. "RECU" or
"JUSTIFICATIF") or reuse an existing identifier already produced inside the
`record_credit_payment` transaction.

## Decision

The debt receipt reuses the `customer_ledger.sequence_no` / `entry_id` value
already generated by `record_credit_payment`'s own transaction as its printed
receipt number. No new `document_sequences` row, key, or migration is
introduced for this purpose.

## Reasons

- The ledger already produces a stable, transaction-scoped integer at zero
  additional engineering cost.
- Introducing a second, parallel numbering scheme under a free-text
  `document_sequences` key would create a second source of truth with no
  proven benefit.
- `DocumentType` (closed enum, 8 sale-document variants) is correctly left
  untouched; debt receipts are not sale documents and must not be forced
  into it.

## Consequences

- TASK-BRK-061 (transactional wiring, not yet implemented as of this ADR)
  must source the receipt number from the ledger entry, not from
  `DocumentSequenceRepository::allocate_next`.
- If a future requirement demands an independently auditable, gapless
  receipt-numbering scheme distinct from the ledger's own ids, this decision
  must be revisited by a new ADR.
