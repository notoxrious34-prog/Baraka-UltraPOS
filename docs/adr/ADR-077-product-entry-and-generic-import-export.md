# ADR-077 - Product entry priority, French name with optional Arabic alias, generic import/export
Status: Accepted
Amends ADR-072 and ADR-075
Context: The owner types hundreds of products himself at the start and needs fast keyboard-only entry. Product names are typed in FRENCH; the Arabic name is one optional alias (owner decision, final). The Dolisoft export (AUD-005-C1: D:\Dev\BarakaInbox\liste_aricles.xlsx, 23 products) is all there is in Dolisoft: Ref is not unique (REF-00005 x8, REF-00001 x4), names carry stray/double spaces and embedded units ("1PZ", "25KG"), the only quantities present are all negative, and there are no barcode, category, unit or supplier columns. No Dolisoft-specific import is needed. ADR-072 designed a Dolisoft migration path; ADR-075 restricted import scope to products only.
Decision:
D1. Product entry has priority over file import. The entry screen must support fast keyboard-only entry: save-and-new (one key), duplicate-similar-product, default category and unit remembered for the session, Enter/Tab flow with no mouse needed.
D2. Name model: `name` = French name (required); `name_ar` = ONE optional Arabic alias. No further alias list in v1. No automatic transliteration; the Arabic alias is the mechanism that lets the seller search in Arabic letters for a product whose main name is Latin French.
D3. Normalized search is required. Normalization (applied to stored search keys and to the query): trim; collapse internal whitespace; Unicode case-fold; strip Latin diacritics; strip Arabic tashkeel and tatweel; unify Arabic alef variants (أ إ آ -> ا), alef maqsura/ya (ى -> ي), ta marbuta/ha (ة -> ه). Search covers: French name, Arabic alias, internal code, barcode, foreign reference.
D4. Identity: Baraka always generates its own internal product code. Barcode is optional (a scanned manufacturer barcode, otherwise the internal code is used as the printable barcode). A foreign reference (e.g. Dolisoft "Ref") is stored only as an optional searchable/informational field and is NEVER a uniqueness key.
D5. Duplicate detection key = NORMALIZED French name (per D3 normalization). Duplicates inside the file and against existing products are listed in the pre-commit report and are NOT imported (default = skip). No silent overwrite.
D6. Import formats and parsing: .xlsx and .csv. xlsx must be read without Excel installed. CSV: auto-detect delimiter (comma, semicolon, tab), accept UTF-8 with or without BOM, Windows-1252 fallback. Provide a downloadable template. Column-mapping step with remembered mappings. Money values are parsed from text into integer centimes with NO floating point; accept "1250.50", "1250,50", "1 250,50" and reject ambiguous input into the error report. Do not auto-parse units out of names (units embedded in names stay in the name).
D7. Import flow: file -> mapping -> preview + validation report -> explicit owner confirmation -> commit. Rows without name or without price are excluded and listed in the report. Unknown categories/units found in the file are listed as "will be created" in the preview and created in the same transaction. The commit is ONE transaction: any database error rolls back everything and the report says nothing was imported.
D8. Opening stock starts at ZERO. The v1 import does not set stock; quantity columns are ignored and counted in the report as "ignored"; negative quantities are always ignored. Stock is established through the inventory screen.
D9. Export: full product export to .xlsx and .csv. CSV export: UTF-8 with BOM, semicolon delimiter by default (French-locale Excel friendly). The export columns round-trip with the import template (an exported file must be importable, subject to D5 duplicate skipping).
D10. Barcode label printing for internal codes rises in priority (design/engine tasks to follow; not specified here).
Consequences: ADR-072 is superseded for the Dolisoft-specific path (profiling-gated Dolisoft import, Ref/barcode idempotency) and refined to the generic flow; ADR-075 products-only scope stays and is refined (normalized-name identity, zero opening stock, export round-trip). Future schema needs: `name_ar`, normalized search keys, optional external reference, generated internal code (no migration is written now). Future implementation tasks must include D3/D6 test vectors.
Out of scope: customers, credit, Dolisoft-specific import, product images, update-existing mode ("Update existing products from file" needs a future ADR), FTS5 migration (the engine search stays LIKE-prefix; the FTS migration is a separate future BRK task), UI layouts.
Open items: concrete entry speed targets (validate in static prototypes before React work); import hard limits (max rows/size, set in implementation); opening-quantity import later via a new ADR if the owner requests it; FTS5 migration task; update-existing-from-file mode.
Related: ADR-072 (superseded in part), ADR-075 (refined), ADR-068 (IFU pricing context), ADR-069 (French/Arabic locales), ADR-066 (viewport baseline for the entry screen design).
Validation gate: owner validates the fast entry flow and the import preview in static prototypes before React work.
